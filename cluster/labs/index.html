Setup (one time)

Each lab is a small pretend network: routers and PCs running as containers on the Pi 5, wired together with virtual cables. Nothing touches your real home network, and you can wreck it and reset it as often as you like.

  1. Open PowerShell on your PC and log in to the Pi 5: 
    ssh grayson@192.168.1.35
  2. Get the newest lab files: 
    cd ~/Portfolio && git pull
  3. Install Containerlab, the tool that builds the labs. It asks for your Pi password and downloads about 300 MB once. 
    bash ~/Portfolio/cluster/labs/lab.sh install
  4. Make lab a short command: 
    echo "alias lab='bash ~/Portfolio/cluster/labs/lab.sh'" >> ~/.bashrc && source ~/.bashrc
  5. Check it works. You should see 5 labs: 
    lab list
Some steps need two windows at once, like watching packets in one while you ping in the other. Open a second PowerShell window and ssh in again.

How it works

There are two kinds of devices: PCs (Linux, named pc1, pc2) and routers (FRR, named r1, r2, r3). FRR's commands are almost the same as Cisco's, so this practice carries over to CCNA-style networking.

You typeWhat happens
lab start 1Builds lab 1 (about 20 s). Starting a lab stops whichever one was running.
lab pc1Opens pc1's Linux prompt. Type exit to come back to the Pi.
lab r1Opens router r1's command line (the prompt looks like r1#). Type exit to leave.
lab checkChecks your work and gives hints for anything not done yet.
lab resetPuts the current lab back to how it started.
lab drawA live map of the lab at :50080. Press Ctrl+C to stop it.
lab stopTurns the lab off when you're finished.

The router's three "rooms"

A router command line has levels, and the prompt tells you where you are:

r1#                    look around (show ...)           → configure terminal
r1(config)#            change router-wide settings      → interface eth1
r1(config-if)#         change one port (interface)      → exit (up one), end (all the way out)

Two keys make it much easier: Tab finishes a word for you (conf + Tab → configure), and ? lists what you can type next.

Every device has an eth0. That's the lab's management connection, so ignore it. Your virtual cables are eth1, eth2 and eth3.
Lab 1 · about 20 min

Two PCs, one cable

You'll learn: IP addresses, subnets (/24), ping, ARP and MAC addresses, and how to watch real packets.

  pc1 ─────────── pc2
 eth1             eth1
 10.0.1.1/24      10.0.1.2/24     ← you set these
  1. lab start 1
lab pc1
  2. Look at pc1's network ports: 
    pc1$ ip addr
    Find eth1. Does it have an inet line (an IPv4 address)? It has a link/ether line, which is its MAC address, its hardware name.
  3. Give pc1 an address on the cable: 
    pc1$ ip addr add 10.0.1.1/24 dev eth1
pc1$ ip addr show eth1

    /24 means "the first 3 numbers are the network". So pc1 is on network 10.0.1.x and expects to reach anything from 10.0.1.1 to 10.0.1.254 directly over the cable.

  4. Do the same on pc2 with .2: 
    pc1$ exit
lab pc2
pc2$ ip addr add 10.0.1.2/24 dev eth1
  5. Say hello: 
    pc2$ ping -c 3 10.0.1.1
    You should get 3 replies with times like 0.05 ms. That's your first working network.
  6. See who pc2 has met: 
    pc2$ ip neigh

    This is the ARP table. Before pc2 could send the ping, it shouted on the cable "who has 10.0.1.1?" and pc1 answered with its MAC address. Compare that MAC with pc1's link/ether from step 2.

  7. Watch it happen. In a second window, run ssh grayson@192.168.1.35, then lab pc1, then: 
    pc1$ tcpdump -n -i eth1
    Back in window 1, clear pc2's memory of pc1 and ping again: 
    pc2$ ip neigh flush dev eth1
pc2$ ping -c 2 10.0.1.1

    In window 2 you'll see ARP, Request who-has 10.0.1.1, then ARP, Reply, then ICMP echo request and echo reply. Press Ctrl+C to stop tcpdump.

  8. Break it on purpose. Move pc2 to a different network: 
    pc2$ ip addr del 10.0.1.2/24 dev eth1
pc2$ ip addr add 10.0.2.2/24 dev eth1
pc2$ ping -c 2 10.0.1.1
    It says Network unreachable, even though the cable is still plugged in. Why? (Answer below.)
    Put it back: 
    pc2$ ip addr del 10.0.2.2/24 dev eth1
pc2$ ip addr add 10.0.1.2/24 dev eth1
pc2$ exit
  9. lab check
Answer: why "Network unreachable"?

pc2 now thinks it lives on 10.0.2.x. 10.0.1.1 isn't on its network, so it wouldn't send straight down the cable. It would need a gateway (a router) to reach other networks, and it doesn't have one. That's exactly what lab 2 is about.

Stuck? Run lab check, copy everything in the window, and paste it to Claude with a note on which step you're on.

Lab 2 · about 25 min

One router, two networks

You'll learn: what a router does, router config mode, default gateways, traceroute, and why replies need a way back.

  pc1 ──────── eth1 [ r1 ] eth2 ──────── pc2
 10.0.1.10      10.0.1.1   10.0.2.1      10.0.2.10
 (set)          ←── you set these ──→    (set)
 network 10.0.1.0/24          network 10.0.2.0/24
  1. lab start 2
lab pc1
pc1$ ping -c 2 10.0.2.10
pc1$ ip route
pc1$ exit

    ip route is pc1's map. It only knows 10.0.1.0/24 (its own cable), so it has no idea how to reach 10.0.2.x.

  2. Set up the router. Open it and look first: 
    lab r1
r1# show interface brief
    Both ports are up but have no addresses. Give each side an address: 
    r1# configure terminal
r1(config)# interface eth1
r1(config-if)# ip address 10.0.1.1/24
r1(config-if)# exit
r1(config)# interface eth2
r1(config-if)# ip address 10.0.2.1/24
r1(config-if)# end
r1# show ip route

    You'll see two lines starting with C, for connected. The router knows both networks because it's plugged into both.

  3. Tell pc1 to use r1 as its gateway ("for anything not on my cable, ask r1"): 
    r1# exit
lab pc1
pc1$ ip route add default via 10.0.1.1
pc1$ ping -c 3 10.0.2.10
    Still no replies! pc1's ping reaches pc2 now. So what's going wrong? Think about it before you look.
    Answer

    pc2 gets the ping and tries to reply to 10.0.1.10. That isn't on pc2's network, and pc2 has no gateway, so the reply goes nowhere. Every conversation needs a route in both directions. This is the number-one networking mistake, even for pros.

  4. Fix the way back: 
    pc1$ exit
lab pc2
pc2$ ip route add default via 10.0.2.1
pc2$ ping -c 3 10.0.1.10
pc2$ traceroute -n 10.0.1.10

    traceroute lists every router along the way: 10.0.2.1 (r1), then pc1.

  5. (Optional) Save the router's settings so they survive a router restart. lab reset still wipes everything: 
    lab r1
r1# write memory
r1# show running-config
  6. lab check

Stuck? Paste the output of lab check, plus show ip route from r1, to Claude.

Lab 3 · about 30 min

Three routers in a row

You'll learn: static routes, next hops, the way back (again), and why typing routes by hand doesn't scale.

pc1 ── [r1] ──────── [r2] ──────── [r3] ── pc2
.10   .1   .1      .2    .2      .3   .1   .10
10.0.1.0/24   10.0.12.0/24   10.0.23.0/24   10.0.3.0/24

Pattern: on links between routers, router N's address ends in .N
(r1 is 10.0.12.1, r2 is 10.0.12.2 and 10.0.23.2, r3 is 10.0.23.3)

Every address and both PC gateways are already set. What's missing: each router only knows the networks it's plugged into.

  1. lab start 3
lab r1
r1# show ip route
    Which of the 4 networks does r1 know about? Which ones are missing?
  2. Teach r1 the way to pc2's network. A static route says "to reach this network, hand it to this next router". The next router must be one r1 is directly connected to: 
    r1# configure terminal
r1(config)# ip route 10.0.3.0/24 10.0.12.2
r1(config)# ip route 10.0.23.0/24 10.0.12.2
r1(config)# end
r1# show ip route

    New lines starting with S, for static.

  3. Follow the packet: 
    r1# exit
lab pc1
pc1$ traceroute -n -w 1 10.0.3.10
    You see r1 (10.0.1.1), then only * * *. The packet really did reach r2, so why can't r2 answer?
    Answer

    r2 has no route back to 10.0.1.0/24, so its "I'm hop 2" reply has nowhere to go. It also has no route onward to 10.0.3.0/24. The way back matters again.

  4. Now it's your turn. Without copying a full answer, add the routes r2 and r3 need. Ask yourself, for each router: "Which networks am I not plugged into, and which neighbour should I hand them to?" Don't forget the way back.
  5. Test: ping -c 3 10.0.3.10 from pc1, then lab check.
Hint 1

r2 sits in the middle. It needs a route to 10.0.1.0/24 (go left, to r1 at 10.0.12.1) and one to 10.0.3.0/24 (go right, to r3 at 10.0.23.3).

Hint 2

r3 needs a route back to pc1's network 10.0.1.0/24 (go left, to r2 at 10.0.23.2). It's also nice if it can reach 10.0.12.0/24 the same way.

Full answer
r2(config)# ip route 10.0.1.0/24 10.0.12.1
r2(config)# ip route 10.0.3.0/24 10.0.23.3
r3(config)# ip route 10.0.1.0/24 10.0.23.2
r3(config)# ip route 10.0.12.0/24 10.0.23.2

Shortcut: r3 only has one way out, so one default route covers everything: ip route 0.0.0.0/0 10.0.23.2.

You typed about 7 routes for 3 routers. A real company network has hundreds of routers. And if a cable breaks, static routes don't notice. Lab 4 fixes both problems.

Stuck? Paste lab check and show ip route from all three routers to Claude.

Lab 4 · about 30 min

Triangle + OSPF

You'll learn: dynamic routing with OSPF, neighbours, route costs, and automatic failover when a cable breaks.

                 [r2]
          .2 /         \ .2
   10.0.12.0/24       10.0.23.0/24
          .1 /           \ .3
pc1 ── [r1] ───────────── [r3] ── pc2
.10   .1   .1  10.0.13.0/24  .3  .1   .10
10.0.1.0/24 (r1 eth1)    10.0.3.0/24 (r3 eth2)
r1: eth2 → r2, eth3 → r3        r3: eth1 → r2, eth3 → r1
  1. lab start 4
    All addresses are set, and there are no routes yet.
  2. Turn on OSPF on r1. The network line means "talk OSPF on every port whose address is inside 10.0.0.0/16, and share those networks": 
    lab r1
r1# configure terminal
r1(config)# router ospf
r1(config-router)# network 10.0.0.0/16 area 0
r1(config-router)# end
r1# exit
  3. Do exactly the same on r2 and r3 (lab r2, lab r3).
  4. Wait about a minute (OSPF waits 40 s before picking a leader on each cable), then see who found whom: 
    lab r1
r1# show ip ospf neighbor
r1# show ip route ospf

    You want two neighbours in state Full, and routes marked O that you never typed. The routers told each other.

  5. Which way does traffic go? 
    lab pc1
pc1$ traceroute -n 10.0.3.10
    It goes r1 → r3 directly, the shortest path.
  6. Cut a cable. In a second window, run lab pc1 and leave this running: 
    pc1$ ping 10.0.3.10
    In window 1, unplug r1's cable to r3: 
    lab sh r1
r1 bash# ip link set eth3 down
r1 bash# exit

    Watch the ping in window 2. It keeps going, or misses a beat or two. Run the traceroute again: traffic now goes the long way through r2. That's failover, and nobody had to touch anything.

  7. Plug it back in: lab sh r1 then ip link set eth3 up. Within about a minute, traffic is back on the short path.
  8. (Bonus) Make the direct cable "expensive" so OSPF prefers the long way even when it works: 
    r1(config)# interface eth3
r1(config-if)# ip ospf cost 100
    Do the same on r3's eth3, then traceroute again. Set it back with no ip ospf cost.
  9. lab check
    The check needs all three cables up, because it expects 2 neighbours per router.

Stuck? Paste lab check and show ip ospf neighbor from each router to Claude.

Lab 5 · 20–60 min

Fix the broken network

This is the real job. Someone "finished" the lab 3 network, but pc1 can't reach pc2. There are 3 problems hidden in it. Find them using only commands. Don't open the files.

pc1 ── [r1] ──────── [r2] ──────── [r3] ── pc2
.10   .1   .1      .2    .2      .3   .1   .10
10.0.1.0/24   10.0.12.0/24   10.0.23.0/24   10.0.3.0/24

The method (works on any network)

  1. Start at the source. On pc1: is the address right (ip addr)? Is the gateway right (ip route)? Can it ping its own gateway?
  2. Walk the path one hop at a time. From each router, ping the next router. Where does it stop working?
  3. Check the ports on each router: show interface brief. Is everything that should be up actually up?
  4. Check the maps: show ip route on each router. Is there a route there and back?
  5. Test both directions. pc1 → pc2 and pc2 → pc1 can fail in different places.
lab start 5
lab check

lab check tells you how many of the 3 you've fixed, but not which ones.

Hint 1 (problem near pc1)

Compare pc1's ip route with r1's actual address on that cable.

Hint 2 (problem in the middle)

Run show interface brief on r2. Someone may have switched a port off with shutdown.

Hint 3 (problem near pc2)

Once pings from pc1 reach pc2, can pc2 reply? Check r3's show ip route for a way back to 10.0.1.0/24.

Full answers
pc1$ ip route replace default via 10.0.1.1      # gateway was 10.0.1.254
r2(config)# interface eth2
r2(config-if)# no shutdown                        # port was switched off
r3(config)# ip route 10.0.1.0/24 10.0.23.2           # no way back to pc1

Stuck? Tell Claude what you've checked and paste the outputs. Claude can coach you with questions instead of just giving the answer, if you ask.
